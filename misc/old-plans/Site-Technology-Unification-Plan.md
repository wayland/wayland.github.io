# Site Technology Unification Plan

## 1. Goal

Share **one** set of XSL stylesheets and shared data files (`siteslist.xml`,
`structure.xml`, the `all-sites` CSS) across all the sites — starting with the
main site (`github-website`) and the Programming Productivity / TOP site
(`PP-site`), and extending to future sites (Perfects, OTTTER, Raku DOPE, etc.) —
so that layout/behaviour is maintained in a single place.

> Status: Stages 1–7 done (main + TOP share `/all-sites/`; §9 verified; TOP live
> in siteslist; OQ-A–E resolved). Next: optional/future — other sites, §10.

## 2. Background: current state

1. **Main site** — 10 XSL files, modular: `all-sites/layout.xsl` +
   6 `<xsl:include>`s (`bibleref`, `cards`, `site-content-main`, `footnotes`,
   `page-contents`, `section-contents`, `menu`) + 2 autogenerated
   (`site-contents.xsl`, `rss.xsl`).
2. **PP site** — 1 monolithic `interface/layout.xsl`.
3. The PP `layout.xsl` is an **older fork** of the main `layout.xsl`, from before
   it was split into modules.
4. **Stylesheet references:** main pages use `/all-sites/layout.xsl` (absolute)
   or `../../../all-sites/layout.xsl`; PP pages use `../interface/layout.xsl`
   (relative, depth varies).
5. **Title source:** main uses `page/title`; PP uses site-contents `@name`.
6. **References:** main routes `<ref>`/`<footnote>`/`<biblio-ref>` through
   `footnotes.xsl` (Footnotes block + bibliography); PP renders `<ref>` inline
   with a bottom "References" section.

### 2.1 Deployment model (important)

1. **No page-build step.** Pages are served as **static XML** and transformed
   **client-side by the browser** via the `<?xml-stylesheet?>` PI. `doco-server`
   just runs `python -m http.server`.
2. There *is* a small **content-generation** step (`autogenerated/bin/generate`,
   Raku) that shells out to `xsltproc` to build `this-site/generated/files.xml`,
   `site-contents.xml`, and `rss.xml`. It is run manually and is currently
   hardcoded to `@paths = <blog>`.
3. All repos deploy to the **same origin**, `wayland.github.io`: the root repo at
   `/`, project repos at `/<repo>/` (e.g. the TOP site at
   `/table-oriented-programming/`).

### 2.2 Why sharing works with this model

1. **Absolute URLs share automatically.** A reference to `/all-sites/layout.xsl`
   (or `/all-sites/structure.xml`, `/all-sites/siteslist.xml`, `/all-sites/*.css`)
   resolves to the **root repo's** files from *any* project page, because they
   share the `wayland.github.io` origin.
2. **`document()` follows the XSL's base URI.** Relative `document('structure.xml')`
   / `document('siteslist.xml')` calls inside `layout.xsl` resolve relative to the
   stylesheet's location (`/all-sites/`), so a **single shared** `structure.xml`
   and `siteslist.xml` are picked up automatically — exactly the intent (see the
   commented-out entries in both files).

## 3. The list: what needs to change

### 3.1 Where the shared XSL lives
1. Treat the root repo's `all-sites/` tree as the single source of truth.
2. The PP repo **no longer needs its own XSL** — its pages reference
   `/all-sites/layout.xsl`. `interface/layout.xsl` in the PP repo is retired.

### 3.2 Page stylesheet references (PP pages)
1. Repoint every PP page's `<?xml-stylesheet?>` PI from `../interface/layout.xsl`
   (varying depth) to the root-absolute `/all-sites/layout.xsl`.

### 3.3 Data files the shared XSL expects (PP is missing several)
1. `document('siteslist.xml')` → the multi-site top bar. Shared from `/all-sites/`
   (already exists; PP inherits it).
2. `sitecontents` = `document('../{sitedir}/this-site/generated/site-contents.xml')`.
   PP currently uses flat `document('site-contents.xml')`; it must adopt the
   `this-site/generated/` layout under its deploy path.
3. `site-index` = `document('/{sitedir}/index.xml')/page` — needs a per-site
   `index.xml` with a `<title>`.
4. CSS: shared `/all-sites/interface.css`, `/all-sites/content.css` (absolute →
   shared) plus a per-site `{sitedir}/this-site/site-styling.css`. PP's `TOP-*.css`
   fold into that split (see §7).
5. `structure.xml` — shared from `/all-sites/` (only `window/base/@href` is
   actually consumed; the `<menubar>` block appears to be legacy/unused).

### 3.4 Input-XML vocabulary changes in PP pages
1. **Title:** add an explicit `<title>` per page (Decision D4).
2. **`sitedir` semantics:** main uses `sitedir` as the *site/deploy* identity
   (e.g. `blog`); PP uses it as the *top-level content folder*. Must reconcile
   (Decision D5).
3. **Fill in the optional-but-read elements to match the main site.** The main
   site populates (per `blog/templates/article.xml`): `<title>`, `<description>`,
   `<category>`, `<author name>`, `<pubDate>`, `<sitedir>`, `<filename>`. Since
   these are filled in on the main site, PP pages should get them too (Decision
   D6). Also read by the XSL: `page/width` (landing pages),
   `page/content/@type` (`blog-index`/`bibliography`), `page/content/@bibliography`.

### 3.5 Behavioural differences to accept
1. **References rendering changes** for PP: `<ref>` moves from the old inline +
   "References" section to the shared **Footnotes** block. (Files to eyeball are
   in §9, Manual Review.)
2. PP **gains for free**: the siteslist multi-site bar, landing pages
   (`width='landing'`), blog cards (`cards.xsl`), Bible blockquotes
   (`bibleref.xsl`), heading anchor links.
3. PP CSS must provide the variables/classes the shared XSL + `menu.xsl` injected
   styles assume (`--site-hue`, `--menu-bar-background-color*`, card variables).

## 4. Decisions

- **D1 — Parameters / architecture.** Keep the pure client-side
  `<?xml-stylesheet?>` model. The browser PI mechanism **cannot pass XSLT
  parameters** (that would need a JS `XSLTProcessor.setParameter()` bootstrap or a
  server-side processor). Continue "passing" context via elements in the page XML
  (`<sitedir>`, `<filename>`, …) and `document()` lookups. No JS bootstrap, no
  page-build step.
- **D2 — Nothing to port from PP.** PP's `layout.xsl` is a strict older fork;
  every template exists in main's modular set in equal or enhanced form. The only
  PP-only behaviour is the older reference rendering (superseded by
  `footnotes.xsl`). So no XSL needs porting PP → main.
- **D3 — Shared `siteslist.xml` + `structure.xml`.** All sites share the single
  `/all-sites/siteslist.xml` and `/all-sites/structure.xml`. Uncomment / fill in
  the PP entries when the TOP site goes live.
- **D4 — Add an explicit `<title>` to every page (content rewrite).** Rewrite each
  PP page so it carries a `<title>` in its metadata; the shared XSL just uses
  `page/title`. The migration promotes each page's current **first `<h1>`** into
  `<title>…</title>` and **removes that `<h1>` from the content** (no duplication
  in body or TOC). One-time, scriptable pass over PP pages (main pages already
  have `<title>`). **Markup inside the heading is preserved** in the `<title>`.
- **D5 — `sitedir` = deploy slug.** Each site uses a single `sitedir` equal to its
  deploy subpath (PP → `table-oriented-programming`), not per-folder values. PP's
  `site-contents.xml` nests its sections under that one `sitedir`.
- **D6 — Populate the standard metadata on PP pages.** Because the main site fills
  them in, PP pages should also get `<title>`, `<description>`, `<category>`,
  `<author name>`, `<pubDate>`, `<sitedir>`, `<filename>` (matching
  `blog/templates/article.xml`).
- **D7 — Dev server routes multiple checkouts + rewrites base href.** Replace the
  local Python `doco-server` with **`misc/serve-locally`** (Raku + Cro) that maps
  path prefixes to the different local checkouts and rewrites the production
  `<base href>` to `localhost` on the way through, so the committed
  `structure.xml` can keep the *production* URL (see §5, §6.2, OQ-B).
- **D8 — Public URLs omit `index.xml`; matching keeps it.** Links and `href`s
  shown to users (siteslist, menus, breadcrumbs, etc.) should prefer directory
  form (`/blog/`, `/table-oriented-programming/`) rather than `…/index.xml`.
  Internal filename matching in XSLT (`page/filename`, `article/@href`,
  `series-url`, `document('/{sitedir}/index.xml')`, etc.) still uses the explicit
  `index.xml` basename so lookups stay unambiguous.

## 5. Suggested filesystem structure

Put all the checkouts as siblings under one parent, mirroring the production URL
layout:

```
~/src/github-websites/
  github-website/               → served at /                (root site; owns /all-sites/)
    current-web → main
    main/misc/serve-locally     → Cro HTTP server: prefix routing + base-href rewrite (D7)
  table-oriented-programming/   → served at /table-oriented-programming/   (today's PP-site)
    current-web → main
  perfects/                     → served at /perfects/        (future)
  ottter/                       → served at /ottter/          (future)
  ...
```

Notes:
1. The **root repo's contents live at `/`** (not `/github-website/`), so
   `/all-sites/...` resolves into `github-website/all-sites/...`.
2. Each **project repo is served at `/<repo>/`**, matching GitHub Pages.
3. The current checkouts differ from this (`~/src/github-website/main` and
   `~/src/TOP/PP-site`); adopting the structure is part of Stage 2 (§6.2).
4. `misc/serve-locally` (Cro) replaces the bare `python -m http.server` in `doco-server`; it
   (a) routes via each repo's `current-web` symlink (`/` →
   `github-website/current-web/`, `/<repo>/…` → `<repo>/current-web/…`), and
   (b) intercepts `structure.xml` to swap `base href` prod→localhost (D7 / OQ-B).

#### 6.2.1 Sibling-checkout layout

**Cursor / workspace caution:** physically moving or renaming the currently open

### 6.4 Stage 4 — PP content migration

Goal: bring every PP content page's metadata in line with what the shared
`layout.xsl` already reads (§3.4), so Stage 6 can switch PIs without a mass
follow-up edit. Pages stay on `interface/layout.xsl` + `TOP-*.css` until Stage 6.

**Depends on:** Stage 3 (§6.3) for the eventual `site-styling.css` path. **Decisions:**
D4, D5, D6. **Also:** §3.4; §9.2; OQ-D. **Template:** `blog/templates/article.xml`.

#### 6.4.1 Scope

1. Rewrite **content pages** under the PP repo (the `*.xml` trees that use
   `<?xml-stylesheet … interface/layout.xsl?>`).
2. **Exclude** non-page XML (`site-contents.xml`, anything under `interface/`,
   generated output once it exists) — those are Stage 5 (§6.1(5), OQ-C).
3. Prefer a **one-time scriptable pass** (Raku / `xmlstarlet` / XSLT) with a
   dry-run that lists D4 edge cases into §9.2; hand-edit only the flagged pages.

#### 6.4.2 Titles from first `<h1>` (D4 / §3.4(1))

For each page whose first content heading is an `<h1>`:

1. Insert `<title>…</title>` in the page metadata, copying the **inner markup**
   of that `<h1>` (D4: markup preserved — not text-only normalisation).
2. **Remove** that `<h1>` from `<content>` so the shared layout does not
   duplicate it in the body or TOC.
3. Leave later `<h1>`s (and all `<h2>`+) untouched.

**Edge cases → §9.2 / OQ-D.** Flag for Manual Review (do not guess) any page
where:

1. there is **no** `<h1>` at all;
2. the first block in `<content>` is **not** an `<h1>` (e.g. lead paragraphs or
   a `.blockquote` before the first heading — common on PP today);
3. the page is a landing / index-like surface with no natural heading.

Record each path under §9.2 as the script finds them; resolve titles by hand
(OQ-D) before Stage 6.

#### 6.4.3 `sitedir` = deploy slug + `filename` rewrite (D5 / §3.4(2))

Shared XSL builds paths as `{$sitedir}/{$filename}` (see `layout.xsl`:
`concat($sitedir_string, page/filename)`), and loads
`{$sitedir}/this-site/…` and `/{sitedir}/index.xml`. Main-site convention:
`sitedir` = deploy identity (`blog`), `filename` = path *under* that identity
(e.g. `raku/general/…xml`).

PP today uses `sitedir` as a **top-level content folder** (`TOP`, `Metanoias`,
`Raku-TOP`, …) and `filename` as a path under that folder. Migrate each page to:

1. `<sitedir>table-oriented-programming</sitedir>` (D5).
2. `<filename>` = old-sitedir + `/` + old-filename when an old folder-`sitedir`
   was present (e.g. `TOP` + `Introduction/What.xml` →
   `TOP/Introduction/What.xml`); if there was no `<sitedir>`, set `filename` to
   the path relative to the PP deploy root.
3. Special cases (root `index.xml`, `filename` of `/`, missing `filename`):
   list under §9.2 and fix by hand so Stage 5's `/{sitedir}/index.xml` lookup
   still works.

`site-contents.xml` nesting under the single deploy `sitedir` is **Stage 5**
(generator / OQ-C) — do not regenerate it in this stage.

#### 6.4.4 Remaining standard metadata (D6 / §3.4(3))

Populate every content page to match `blog/templates/article.xml`:

1. `<title>` — D4 (§6.4.2) or hand title from §9.2 / OQ-D.
2. `<description>` — write a one-line summary if missing (prefer real text over
   leaving `TODO`).
3. `<category>` — derive from section path / site-contents section name where
   obvious; otherwise hand-fill.
4. `<author name>` — default `Tim Nelson` (matches main template / PP tagline)
   unless a page already has a different author.
5. `<pubDate>` — keep existing if present; otherwise leave a clear placeholder
   or omit and accept the shared layout's date fallback until known.
6. `<sitedir>` / `<filename>` — §6.4.3.

Optional attributes the shared XSL also reads (`page/width`,
`page/content/@type`, `page/content/@bibliography`) — set only where the page
actually is a landing / blog-index / bibliography surface; do not invent them
for ordinary articles.

2. §9.1 (references → footnotes) is **eyeballing at Stage 7** after the Stage 6

3. After the batch rewrite, spot-check a few pages under PP's *current* layout
   (still `interface/layout.xsl`) to ensure removing the promoted `<h1>` did not

#### 6.4.6 Explicitly deferred

1. **PI switch** to `/all-sites/layout.xsl` — Stage 6 (§3.2, §6.1(6)).
2. **`this-site/generated/`**, regenerating `site-contents.xml`, creating/adjusting

#### 6.5.1 What the shared layout expects

#### 6.5.2 Generalise the generator (OQ-C)

Today `autogenerated/bin/generate` (root repo) is hardcoded to `@paths = <blog>`
and shells out to `xsltproc` + `xml_pp` to build, under each path:

1. `this-site/generated/files.xml`
2. `this-site/generated/site-contents.xml` (via `autogenerated/xsl/site-contents.xsl`)
3. `this-site/generated/rss.xml` (via `autogenerated/xsl/rss.xsl`)

**Do:**

1. Take an explicit path / site argument (and/or a list), not a hardcoded `blog`
   (OQ-C) — so the same script can target the PP checkout (sibling
   `table-oriented-programming/current-web` or equivalent) as well as `blog`.
2. Parameterise anything else in `generate` / the XSL that assumes `blog`
   (output paths, `xml:base`, titles).
3. Keep one generator in the **root** repo; do not fork a PP-only copy.

**PP-shaped contents (important):** `site-contents.xsl` supports two structures via
`$structure` (`series` | `tree` | `auto`):

1. **series** (blog) — sections from `index.xml` + `page/series-dir` (unchanged idea).
2. **tree** (PP) — nest sections from the directory tree under the deploy slug;
   article titles from each page’s `<title>`; section titles from folder names
   (hyphens → spaces). Curated hand labels (e.g. “Overview”, “Editors”) are
   **not** preserved — nav follows the filesystem.
3. **auto** (default) — `series` if any page has `series-dir`, else `tree`.

Article `@href` values **must** match `concat(sitedir, '/', page/filename)` or
Stage 6 nav/title lookup fails.

**Done (Stage 5):** `generate` takes site path args; one generalised
`site-contents.xsl` (no hand-file bridge). Hand `interface/site-contents.xml`
remains the interim nav source until Stage 6. Regenerate with
`autogenerated/bin/generate ../../table-oriented-programming/current-web`.

## 10. Future Separation of PP Site

Today Programming Productivity / TOP is one deploy slug
(`table-oriented-programming`) with several content areas (TOP, Raku-TOP,
Metanoias, RAD, …) under a single `sitedir` (D5). At some point those areas
may become separate sites (or PP may split from TOP) with their own deploy
paths, `this-site/`, and generated `site-contents`.

When that happens, **rejig site-contents generation** for the split sites:

1. The current **`structure=tree` / `emit-tree`** path in
   `autogenerated/xsl/site-contents.xsl` exists only because one combined site
   has no blog-style `series-dir` metadata and must invent nav from the
   filesystem. After separation, prefer real section/series metadata (or
   curated structure) per site rather than growing the tree walker.
2. Revisit whether each new site should use **`series`**, a thinner tree, or
   something else; drop or narrow `tree` mode if it is no longer needed.
3. Update `this-site/site-config.xml`, `siteslist.xml` (D8 hrefs), and page
   `<sitedir>` / `<filename>` for each new deploy slug.
4. Keep generator in the root repo (OQ-C / §6.5.2); point it at each sibling
   checkout — do not fork a per-site `generate`.
